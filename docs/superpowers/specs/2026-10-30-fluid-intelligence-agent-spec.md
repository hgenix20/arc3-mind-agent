## 2. What is built

### 2.1 The scored path

The hybrid plays the fluid agent first on each level. It hands the level to the explorer
after `mind_moves` moves or after `STALL_MOVES = 25` fallback moves in a row. The fluid agent
writes no code and makes no LLM call. The explorer covers the screens it can reach.

The fluid agent is built around the paper's four modules, each with a null for ablation
(`arcagent/mind/fluid_modules.py`):

| Paper module | Real | Null |
|---|---|---|
| Voi (choose the next test) | `tester.choose_test` | first untried action with an unknown pair |
| Inhibition (refuse an action) | `tester.veto` | never refuses |
| Metacognition (fact break threshold) | `MissMetacognition` (`BROKEN_MISSES`) | `NEVER_BROKEN` |
| Transfer (carry facts across levels) | `CarryTransfer` | `FactMemory.forget` |

## 4. Conflicts between parts

Each conflict needs one owner before build. These are my proposals, not rulings.

- **C1. Sequence record (Parts 6 and 8).** Part 6 stores completed sequences per goal. Part
  8 keeps a live sequence list, the first moves of the top hypothesis. Proposal: one record
  type with `status` set to `live` or `completed`.
- **C2. Two confidence systems (Parts 1, 7, 8).** Rule status (`candidate`, `validated`,
  `broken`) and the Beta probability both describe reliability. Proposal: status is derived
  from the probability and the evidence thresholds, so one number decides.
- **C3. Index fields (Parts 1 and 2).** The index in Part 2 must cover every field of the rule
  record in Part 1, including `scope` and the canonical key. Build Part 1's schema first.
- **C4. Strategy switches (Parts 3, 7).** The Part 3 controller and the Part 7 gates both end
  a task and hand it to another method. Proposal: the controller owns every handoff, and the
  gates only report.
- **C5. Horizon (Parts 5 and 8).** Part 5's segment bound and Part 8's horizon `H = 5` are
  two names for one value. Proposal: one constant, one owner.
- **C6. Prediction writes (Part 8 against the source).** The source says prediction writes
  only two lists. Part 8 keeps learning as a separate writer (D1). Part 9's flags are also
  written by the learning step. This stands until Kameron rules on Part 8 Q1.
- **C7. Inhibition and adverse estimates (Parts 6, 7).** Part 7 reads adverse probabilities
  from Part 6's rules. Part 6's rules carry evidence counts, not a probability. Proposal:
  the Part 7 Beta is a field of the Part 6 rule record.
- **C8. Self and controller (Parts 3 and existing code).** The "I" and "my character" rule in
  Part 3 overlaps `modes.py` (the active controller). Proposal: `modes.py` supplies the
  character, and the self record is built on it.
- **C9. Shared BFS and the silent stop (Part 4 and `kinematics.py`).** The shared BFS changes
  the function that stops silently at `KIN_LIMIT`. Build the truncation flag before the
  shared function, so the change is one step.
- **C10. Ordering of checks (Parts 5, 7, 9).** Parts 5, 7, and 9 each say a lower-priority
  move waits behind the plan. The ladder in `fluid.py` already does that. Proposal: one
  ladder, with each part's addition written as a step in it.

## 3. Runtime contract

- **Game interface.** Each move gets an `Observation` (`arcagent/core/types.py`): a 64x64
  `int8` grid with values 0 to 15 and padding -1 (`grid_from_frame`), a phase (not played,
  in play, won, game over), `levels_completed`, `win_levels`, and `available_actions`.
  Actions are integer ids. Action 0 is RESET. Action 6 is a click at (x, y). The others are
  simple actions whose effect is not named in the observation.
- **Scoring.** Per level, `min(human_actions / agent_actions, 1)^2` (`docs/agent-submission.md`).
  The per-game score is the mean over levels weighted by level index, and the total is the
  mean over games. The experiment log reports offline results as scorecard means. Public
  leaderboard figures appear in the log in a different unit, and the log does not say how
  the two relate (section 12).
- **Budget.** The entry plays 110 private games in a Kaggle rerun with 9 hours of runtime,
  no internet, and the games' own move counters where the game has one (`budget.py`).
- **Seeds.** A game's seed is the run seed plus its index in the game list (`MindRun`).

## 5. Per-move decision order (the fluid mind)

From the module docstring of `fluid.py`. Branch names are what the run log records.

1. **Game over or not played.** Learn the death from the move that caused it, reset the
   tracker and noise, clear the plan, return RESET (branch `reset`).
2. **Level up.** Record the level-up fact, call `goals.level_up` and `learn_win` (when
   nothing was confirmed), run `fluid_sleep`, reset positions in `FactMemory`, run the
   transfer step, clear the plan and the level's history. The new screen teaches nothing.
3. **Update.** Update tracker, kinds, mode, noise. Learn from the transition, check the last
   prediction. A goal whose plan was being followed and still open is set probing, and a
   commit probe starts (branch `commit`, event `commit_probe`, at most `COMMIT_PROBES = 4`).
4. **Plan.** A plan stops only on a miss that matters (`plan_breaks`). A plan with steps
   left gives the next step (branch `follow`).
5. **Forced and bump.** The only move no plan veto refuses (branch `forced`). A step whose
   goal already holds gets the learned bump move (branch `plan`).
6. **Budget, indicator, test.** A budget-tight partial plan step; an indicator step (branch
   `plan`, why `sequence step` or `sequence try`); the tester's test (branch `learn`), at
   most `MAX_TESTS_PER_ATTEMPT = 200` per level attempt.
7. **Partial plan, then novelty.** The goal search's best partial plan (branch `plan`, why
   `toward <goal id>`); else novelty search (why `explore novel`).

Goal search runs with `SEARCH_MAX_NODES = 3000` predictions and `SEARCH_TIME_S = 1.0` seconds.
A goal fails an attempt when its plan breaks without the goal holding. After `STALL_AFTER =
2` failed attempts in one level, the goal is set aside until the level changes.

## 6. The hybrid's switching rule

- Each level starts with the mind (`HybridPolicy.choose`).
- The mind plays until it has made `mind_moves` moves on the level (the committed hybrid),
  or, with the uncommitted stall rule, until `STALL_MOVES = 25` of its moves in a row were
  fallback moves (branch `fallback`).
- Then the explorer plays the rest of that level.
- A level change gives the mind the next level. If the explorer played last, the mind is
  resumed (`FluidAgent.resume`) so it does not learn from moves it did not make.
- `mind_moves` is 150 in the 2026-10-28 and 2026-10-29 benches and was 400 in the first
  hybrid run. `submit.py` defaults `--hybrid-moves` to 0, which plays the mind alone; the
  notebook passes the value it is given.

## 7. Learning in the fluid mind

- **Facts.** Each move's transition is learned (`facts.learn`). A fact is solid after
  `THIN_BELOW = 5` agreeing observations and broken after `BROKEN_MISSES = 2` misses in a
  row. A miss does not rewrite a fact's effects.
- **Goals.** `GoalBook.level_up` confirms goals at a level-up. Probe-excluded goals are
  credited (`probed`).
- **Learning from a win.** `learn_win` credits the gaps the winning move closed
  (`WIN_GAP = 2`, `WIN_LEARNED = 2`, `WIN_FRAMES = 80`) when no goal was confirmed.
- **Generalising forms.** `generalize_forms` extends reach and cover forms to colours
  (`cN:*`).
- **Sleep.** `fluid_sleep` runs at each level-up and at game end. It demotes facts a winning
  level relied on after misses, logs merge candidates, and drops thin zero-hit facts. Time
  cap `SLEEP_MAX_S = 0.5` per call.
- **Transfer.** `CarryTransfer` keeps facts across levels; the null forgets them.

# Agent Memory Design (Part 1 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Memory" section, pasted 2026-10-30. Where the source and the existing
code disagree, the source governs. The current agent is not scoring well, so the
source is the target and the code is the starting point.

Later parts of the spec will be added as new sections. Numbers in this part refer to
its own sections only.

## 1. Requirements (from the source)

**Working memory**

- **R1 Scope.** Working memory persists through levels. It clears on a full game reset
  or on the start of the next game.
  - Hypothesis H1 (Kameron's): if working memory forces the agent to relearn each game,
    the working memory design gets redesigned. Section 6 says how to test this.
- **R2 Escalation.** A working memory item that is validated moves to long-term memory.
- **R3 Contents.**
  - Current state list: items on the grid, each mapped to its actions, events, and
    interactions with the player (a wall, an enemy, an item, a door, an exit, or
    anything like them).
  - Action list: each action mapped to the events and interactions that occur when it
    is present or called.
  - Goal list: two items in sequence, "complete the level" then "win the game".
  - Task list: a focused list of steps, ranked by sequence.
  - Level rule list: rules organized by object, event, or experience, for the current
    level. The agent identifies objects and guesses events, then pulls the relevant
    rules from the game rule list. If no rule exists during the level, the agent creates
    one.
  - Game rule list: the same organization, scoped to the current game.

**Long-term memory**

- **R4 Scope.** Long-term memory persists between games.

The source does not say what a validated item is, what long-term memory stores beyond
rules, or what gets loaded at the start of a game. Section 5 proposes answers and marks
them as decisions.

## 2. What the current code does

Code paths are the fluid agent (`arcagent/mind/fluid.py`), the path the hybrid runs
(`arcagent/agent/hybrid.py`). The older LLM and program path (`arcagent/mind/agent.py`,
`memory.py`) is not on the hybrid path.

| Requirement | Current code | Status | Gap |
|---|---|---|---|
| R1 scope: game | A new `FluidAgent` and fresh modules per game (`config.py` `build_modules`: "modules hold no cross-game state"). | Built | None for the game boundary. |
| R1 persistence: levels | `FactMemory` keeps facts across level-up and resets only positions (`fluid.py` step 2). | Built | Facts are not split into a level list and a game list. Scope is a `level` stamp on each fact. |
| R1 persistence: game over | A game-over RESET keeps facts and clears the plan (`fluid.py` step 1). | Built | Source says working memory clears on a full game reset. Whether a RESET after game over is a full reset is open (Q1). |
| R3 current state list | `objects.py` (`Thing`, `Scene`), identity across looks in `kinds.py`. | Partial | Things have no event or interaction list. Interactions live only in facts keyed by subject and label. |
| R3 action list | `FactMemory` facts keyed by subject, label, and context, with effects. | Partial | Facts are keyed by action, not organized as a per-action list. |
| R3 goal list (level, game) | `GoalBook` holds guesses (reach, clear, match, cover, sequence, match_thing). A level-up confirms a goal. | Partial | No "win the game" goal. No two-tier list. |
| R3 task list | Plan from `search.py` and `route.py`. `goals.ranked` orders goals. | Partial | The plan is a path to one goal, not a ranked task list. |
| R3 level rule creation | `FactMemory.record` creates a fact when evidence is new. | Built | The fact is not filed under a level rule list. |
| R2 escalation | None. `fluid_sleep` demotes facts a winning level relied on after misses, merges siblings, and drops facts with zero hits. | Missing | Nothing promotes a fact to a longer-lived store. |
| R4 long-term memory | None on the fluid path. `GameStore` and `WorkingMemory` (`memory.py`) belong to the LLM path. | Missing | No store survives the game. |

**Why this matters for the score.** A game starts with zero knowledge. What a click does,
what a wall blocks, and what a key opens are relearned in every game, even when the
same mechanic appeared in an earlier game. The fact keys also use the color index
(`sig` includes color). The 25 games use different color subsets (survey of first
frames, 2026-10-29), so a key built on color would not transfer across games even if
it were stored. A cross-game key has to name kind and role, not color.

## 3. Proposed structure

Three stores, with one schema for every rule.

**Rule record.** Every rule in working memory and long-term memory has the same fields.

- `id`: stable within its store.
- `kind`: `object`, `action`, `event`, or `experience`.
- `subject`: a thing kind (not a sig) for cross-game rules, or a sig within a game.
- `effect`: what happens, in the existing effect vocabulary.
- `scope`: `level`, `game`, or `long`.
- `created_level`, `created_game`: where the rule was first seen.
- `hits`, `misses`: evidence counts.
- `status`: `candidate`, `validated`, or `broken`.
- `source`: `learned` or `loaded` (from long-term memory).

**Goal record.** Scope `level` or `game`, a statement (the goal kind and its arguments),
and a status (`open`, `probing`, `reached`, `excluded`). "Win the game" is a game-scope
goal.

**Stores.**

- **Level rules** are the rules with scope `level`. `new_level` drops them, except those
  promoted to game scope.
- **Game rules** are the rules with scope `game`. They are cleared on a full game reset
  or at the start of the next game.
- **Long-term rules** are the rules with scope `long`. They are loaded at game start and
  saved at game end.

The existing `FactMemory` becomes the store for level and game rules. It already stamps
each fact with its level, and `fluid_sleep` already moves evidence between states. The
change is to add `scope` and the canonical key, not to replace the class.

## 4. Behavior

- **Creation.** A rule is created when the agent sees evidence no rule covers. It starts
  as `candidate` with scope `level`.
- **Promotion inside a game.** A candidate becomes `validated` when it reaches the solid
  threshold (`THIN_BELOW = 5` agreeing observations, the existing constant) and has no
  miss in the level where it was used. A validated rule created on one level is promoted
  to scope `game`.
- **Escalation to long-term (R2).** A game-scope rule that is validated and used in a
  winning level is written to long-term memory with scope `long`.
- **Loading.** At game start, long-term rules are loaded as `candidate` with
  `source = loaded`. They are not validated, so the first miss on a loaded rule breaks
  it. A loaded rule that the new game confirms is promoted as usual.
- **Breaking.** A rule breaks after the existing `BROKEN_MISSES` misses in a row. A
  broken long-term rule is kept with its miss count, not deleted, so the log shows it.
- **Clearing.** On a full game reset, game rules and level rules are cleared. Long-term
  rules are kept.

Every create, promote, load, break, and clear writes a log event with the rule `id`, so
an ablation can count them.

## 5. Decisions I made

These are my calls. Each one can be changed without changing the requirements in
section 1.

- **D1.** Cross-game keys use thing kind and role, not color index. Reason: color
  subsets differ per game (section 2).
- **D2.** Loaded long-term rules start as `candidate`. Reason: a rule learned in one game
  can be wrong in another, and one miss should be enough to drop it.
- **D3.** Validated means `THIN_BELOW` agreeing observations and no miss on the level
  where it was used. The source does not give a number, so I reused the existing
  constant. Reason: it keeps one definition of "solid" in the code.
- **D4.** Long-term memory is a file written at game end and read at game start. It is
  never written during scoring unless Q2 says it should be.

## 6. Test plan

**H1 (relearning cost).** For each game, record moves to the first level-up and to the
first win, from a run with an empty long-term store. Then run again with the store
filled from other games, on games the store has not seen. Compare the two.

- A drop in moves on the second run supports H1 and the long-term design.
- No drop means the relearning cost is not in the rules, and the working memory redesign
  needs a different cause.

**Level transfer (6.1, 6.3).** Moves to level n+1 against moves to level n within a game,
with and without the working memory carry.

**Held-out games.** The 25 games are all public and have been used for tuning. Q4 asks
for a split. Every memory change is judged on games not used to tune it.

**Unit tests.** Each rule transition in section 4 has a test that checks its log event.
Each store's clear rule has a test: game rules and level rules clear on game reset, long-term
rules do not.

## 7. Open questions for Kameron

- **Q1.** After a game over, does RESET restart the same level or the whole game? The
  answer decides whether working memory clears on game over, or only on a full reset as
  the source says.
- **Q2.** Should long-term memory update during a scored run, so that games in the same
  run help each other? Or should it be a file built before the run?
- **Q3.** What makes a rule validated for escalation to long-term memory: a count of
  observations, a number of levels, or a number of games?
- **Q4.** Which games are the held-out set for memory changes? All 25 games are public
  and were used for tuning.

# Fluency Retrieval Design (Part 2 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Fluency Retrieval" section, pasted 2026-10-30. The source governs
where it differs from the current code. Part 1 (`2026-10-30-agent-memory-design.md`)
defines the rule records and the three stores that this part retrieves from.

## 1. Requirements (from the source)

- **F1 Speed and accuracy.** The agent retrieves the most accurate information the
  fastest, without sorting through every stored item before reaching the most probable
  answer.
- **F2 Index, not scan.** The source's example: a reader doesn't read the whole
  dictionary to find a word starting with Z. Retrieval should reach the candidates
  directly and stop there.
- **F3 Meaning-based keys.** A network of meanings and keys may improve accuracy. The
  source leaves the form open.

The source does not define "most probable answer," the size of the candidate set, or
what counts as a retrieval. Section 5 proposes those and marks them as decisions.

## 2. What the current code does

Retrieval happens in four places. Two are indexed and two scan.

| Retrieval | Current code | Access pattern | Status |
|---|---|---|---|
| Fact by (action, subject, context) | `FactMemory.lookup` (`facts.py`) reads the `facts` dict by exact key, then falls back in a fixed order: the subject's `any` fact, the kind's facts, a broken fact, a same-shape sibling, the action-wide fact. | Hash lookup, then a fixed chain. | Indexed. The order is fixed, not ranked by probability. |
| Sibling fact (same action, same shape) | `FactMemory._borrow` reads `_siblings[(label, context, shape)]` and picks the most hits, ties to the lowest key. | Index lookup, then a min over the candidates. | Indexed. Only exact shape match counts, so a thing with the same role and a different shape is not found. |
| Facts by behavior tag | `FactMemory.toc` maps tag to keys. `by_tag` returns them sorted. | Index lookup. | Indexed. Tags are the only semantic key. |
| Gaits for one subject | `kinematics.py` `gaits` sorts all facts and filters by subject on every call. | Full scan and sort. | Scan. |
| Movers, controlled things, clear colors, pushed sigs, restyle families | `goals.py` helpers (`_mover_sigs`, `controlled_sigs`, `_clear_colors`, `_pushed_sigs`, `restyle_families`) loop over every fact each time they run. | Full scan per call. | Scan. |
| Goal guesses | `GoalBook.guesses` rebuilds the candidate list from the current scene on every call, with reach guesses capped at `MAX_REACH_TARGETS`. | Rebuilt per call from the scene, not stored. | Bounded but not indexed. |

Three gaps follow from this.

1. **Scans run on the hot path.** `gaits` and the goal helpers read the whole fact table
   on every call. Their cost grows with the number of facts, and Part 1 will grow that
   number, because long-term rules will be loaded at game start. The cost has not been
   measured yet.
2. **Nothing ranks by probability.** `lookup` returns the first hit in a fixed order.
   Hit counts are used only to break ties between siblings. A rule with 40 agreeing
   observations and a rule with 5 are treated the same when both match the key.
3. **Nothing matches by meaning.** The only semantic key is the behavior tag, and the
   sibling index needs an exact shape. A thing that plays the same role as a known thing
   with a different shape gets no help from memory.

## 3. Proposed design

Retrieval goes through one contract. Every store implements it, and no caller reads a
store's table directly.

**Query.** A query carries the situation's features: action label, subject kind and
role, shape class, context, and effect tags. Features are the canonical keys from Part 1
(kind and role, not color index).

**Index.** An inverted index maps each feature to the rule ids that carry it. The
existing `toc` and `_siblings` are two instances of this, one keyed by tag and one by
(label, context, shape). The new index covers every feature the query can name, so a
query reads the candidate postings and nothing else.

**Ranking.** Each candidate gets a score from its evidence (hits, misses, status) and
its specificity (how many query features it matches). The retrieval returns the top `k`
with their scores, sorted best first. The default `k` is a decision (D3).

**Fallback.** When no candidate matches, the retrieval returns an empty result. It does
not scan the full table. A caller that needs a broader answer asks for one explicitly,
and the call is logged as `retrieval_fallback` with the query and the store size.

**Confidence.** A returned candidate carries its score, so the predictor and the
metacognition module can read how sure the retrieval was instead of assuming a match.

**Learned scorer (phase 2, not in this build).** A small model maps (query features,
candidate features) to a probability, trained online from the logged hits and misses.
Section 5 explains why it waits for the index.

## 4. Behavior

- **Insert.** When a rule is created or promoted (Part 1 section 4), it is added to the
  index under every feature it carries. When a rule breaks or is dropped, its postings
  are removed. Removal and insert are both logged.
- **Equivalence.** For any query, the indexed retrieval returns the same top candidate as
  a brute-force scan over the same store. The index is a speedup and must not change the
  answer.
- **Scan callers move to the index.** `gaits` and the goal helpers read postings for
  their feature instead of the whole table. Their outputs must match the current outputs
  on the same facts.
- **Bounded work.** A retrieval reads at most the postings for its features. The number
  of postings read is logged per call.

## 5. Decisions I made

These are my calls, changeable without changing section 1.

- **D1. Index before learning.** The index comes first. It is exact, testable, and
  matches the equivalence rule. A learned scorer comes later, only if the index's top
  candidate is measurably wrong often enough to matter. Reason: a learned scorer trained
  on 25 public games risks fitting those games, and the held-out games would show it.
- **D2. No silent scans.** Every retrieval that reads more than its postings is logged.
  Reason: a scan that happens without a record is how the current cost went unnoticed.
- **D3. Default `k` is 5.** The source doesn't give a number. Five is enough for the
  predictor to check a few alternatives without reading the table. It is a starting
  value to test.
- **D4. Probability means the evidence score, not a learned output.** Until D1's learned
  scorer exists, "most probable" means the highest evidence score under a fixed formula.
  The formula is in the code and in the log, so it can be checked.
- **D5. Meaning means canonical features.** A feature is a kind, a role, a shape class,
  or an effect tag. Meaning-based matching in this build is matching on those features.
  A learned embedding of meanings is the phase 2 question, not this build.

## 6. Test plan

**Equivalence (F1, D2).** Record a set of queries from real runs. Run the indexed and
brute-force retrievals on each. Every top candidate must match. Any mismatch fails the
build.

**Speed.** Time each retrieval path with a profiler on the same runs, before and after.
The baseline has not been measured. The first step is to measure the scans, and the
work is worth doing only if they are a meaningful share of move time.

**Accuracy.** Share of queries where the top candidate's predicted next frame matches
the observed frame. This uses the predictor's existing check. It is the number the
learned scorer (phase 2) must beat, if phase 2 happens.

**Scaling.** Retrieval cost against store size, at 10 and 100 times the current fact
count. A flat curve means the index works. A curve that tracks store size means a scan
is still on the path.

**Held-out games.** Same rule as Part 1 section 6. Retrieval changes are judged on
games not used to tune them.

**Unit tests.** Insert and remove keep every posting consistent. An empty query returns
an empty result without reading the table. A `retrieval_fallback` event is logged when
a caller asks for a broader answer.

## 7. Open questions for Kameron

- **Q1.** Is "most probable" the evidence score (D4), or should a rule's age, recency, or
  the level it came from count too?
- **Q2.** Is `k = 5` (D3) right, or should the predictor see every candidate above a
  threshold?
- **Q3.** Should the phase 2 learned scorer be a small neural network, or a tree over the
  same features? The tree is cheaper to run and easier to inspect. The network can learn
  meaning from raw features, but it needs more games to train.
- **Q4.** Does this retrieval construct have a place in the HCQM tree? I have not mapped
  it yet. It may sit under working memory (1.6) or pattern recognition (8.3), and I'd
  check Appendix A before claiming either.

# Metacognition and Self-Identity Design (Part 3 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Metacognition" section, pasted 2026-10-30. The source governs where it
differs from the current code. Parts 1 and 2 (`2026-10-30-agent-memory-design.md`,
`2026-10-30-fluency-retrieval-design.md`) define the stores and retrieval that this part
reads.

## 1. Requirements (from the source)

**Self-identity**

- **S1.** The agent is a player. It is represented as "player", "I", or "Me", depending on
  what information it receives.
- **S2.** When a mouse click and a character are both present, "I" and "Me" stand for the
  mouse click, and "My character" stands for the actionable figure the agent moves
  through controls.
- **S3.** When a mouse click is missing and a character is present, "I" and "Me" stand
  for the character.
- **S4.** When a mouse click is present and a character is not, "I" and "Me" stand for the
  mouse click.

**Metacognition**

- **M1.** Metacognition identifies how the agent is thinking, what it is thinking about,
  and adjusts in real time.

The source does not define "mouse click present," "character present," what "how the
agent is thinking" covers, or which adjustments are allowed. Section 5 proposes
definitions and marks them as decisions.

## 2. What the current code does

**Self-identity**

- There is no self record. The code never labels anything as "I," "me," or "my."
- **Controlled things** are learned from movement, not declared. `goals.controlled_sigs`
  returns the sigs whose things moved under actions.
- **Active controller.** `ModeTracker` (`modes.py`) tags one controlled thing as active
  after a non-click action moves exactly one controlled thing, and only when two or more
  controlled things are on screen. With one controlled thing, its facts stay in context
  `any` and no active tag is set.
- **Clicks.** Action 6 with coordinates is handled by `clicked_thing` and `remap_click`
  (`fluid.py`). A click is an action, not a self.
- **Mouse cursor.** I searched `arcagent/mind` for "cursor" and found nothing. The code
  does not detect a cursor drawn on screen.

Status: partial. The active controller covers S3 when several controlled things exist. S2
and S4 have no implementation, and nothing in the code states which of the two is "I."

**Metacognition**

- **Program confidence.** `ConfidenceMetacognition` (`modules/metacognition.py`) reports
  programs to drop on misses in a row or low fit. It works on the belief of the LLM and
  program path, which the hybrid does not use.
- **Fact breaking.** In the fluid path, `FluidMetacognition` (`fluid_modules.py`) sets the
  fact break threshold, read once when the agent is built (`MissMetacognition` returns
  `BROKEN_MISSES`; its ablation null returns `NEVER_BROKEN`). Facts break after that many
  misses in a row. `ConfidenceMetacognition` is a different module, on the program path.
- **Progress monitor.** `progress.py` names each move `milestone`, `progress`, `regress`,
  or `motion` from goal distances.
- **Stall rule.** `hybrid.py` hands the level to the explorer after `STALL_MOVES` = 25
  fallback moves in a row, or after a fixed number of mind moves per level.
- **Branch labels.** Each chosen move records how it was chosen: `plan`, `commit`,
  `fallback`, `forced`, `reset`, and the tester's labels. The label is logged, and the
  agent reads `last_branch` once, for the hybrid's stall count.
- **Indicator tracking.** `indicator.py` tracks progress indicators and records each
  step as right or wrong.

Status: partial. Each signal is computed and logged, and a few drive a single decision
(the fact break threshold, the stall handover). No component holds a current picture of
what the agent is thinking about, and no component weighs several signals together to
choose a strategy. The branch label is written down but not read by a decision, except
the stall count.

## 3. Proposed structure

Two records, updated once per observation, plus one controller that reads them.

**Self record.** One per observation.

- `role`: `character_and_click`, `character`, `click`, or `none`. This is the S2 to S4
  rule applied to the observation.
- `I`: the referent of "I" and "me" for this observation. `click` in the first case,
  `character` in the second, `click` in the third, `none` in the fourth.
- `my_character`: the tracked id of the controlled thing when one is present, otherwise
  none. Drawn from the active controller when set, else from the single controlled thing.
- `click_at`: the last click coordinate when the action was a click, otherwise none.

**Focus record.** One per observation, the agent's current picture.

- `level`, `goal` (the goal being pursued and its status), `target` (the thing or
  region the goal is about), `mode` (the branch that chose the last move), `budget` (from
  the budget module), and `signals` (the progress, regress, stall, and miss counts).

**Controller.** A fixed table of rules. Each rule reads the focus record and returns one
of: keep the current strategy, switch goal, switch from the mind to the explorer, reset
fact breaks, or re-probe a goal. Every returned action is logged with the rule that
fired.

## 4. Behavior

- **Self record.** Recomputed every observation. The three cases in S2 to S4 are checked
  in the order the source gives. The record is written to the run log so each choice can
  be audited against its self.
- **Click present.** A game counts as having a click when its available actions include
  action 6 (this is the reading in D2).
- **Character present.** A game counts as having a character when `controlled_sigs` is
  non-empty on the current scene.
- **Focus record.** Updated after the goal and mode are chosen for the move, before the
  next move.
- **Controller rules.** Evaluated once per move, in a fixed order. The first rule that
  fires wins. Rules are written as code, with thresholds in one place. No rule is learned
  in this build.

## 5. Decisions I made

These are my calls, changeable without changing section 1.

- **D1. The source's rule is followed as written.** When click and character are both
  present, "I" is the click and "my character" is the controlled thing. This is the
  reading that the source states, even though the character is the thing the agent moves.
- **D2. "Mouse click present" means action 6 is available.** The code has no cursor
  detector, and a cursor is not needed to know whether clicks are a legal action. Reason:
  the action list is exact and already exposed. Cost if wrong: a game that draws a cursor
  but lacks action 6 would be misread. Q1 asks for confirmation.
- **D3. "Character present" means the controlled-thing set is non-empty.** Reason: the
  same set already drives the active controller, so the two cannot disagree.
- **D4. The controller is rule-based in this build.** Reason: a rule table can be read in
  a run log and tested by hand. A learned controller would need the phase 2 scorer from
  Part 2 and more training games than we have.
- **D5. Real time means per move.** Reason: the source says "in real-time," and every
  decision the code makes already happens per move. The controller adds no delay beyond
  the rule checks.

## 6. Test plan

**Self record (S2 to S4).** Fixture scenes for each of the four cases, with expected
`role`, `I`, and `my_character`. The fixtures include the edge cases: a click on empty
ground with a character present, and two controlled things with one active.

**Click and character presence on the real games.** Run the detector on the 25 games and
compare with the action survey from 2026-10-29. The six games whose only action is 6
(`ft09`, `lp85`, `r11l`, `s5i5`, `tn36`, `vc33`) should come out as click-only or
character-free. Any other result is a finding to explain.

**Controller decisions.** For each rule, count how often it fires on a run and whether the
move it caused was followed by progress. A rule that fires often and rarely helps is a
candidate for removal.

**Stall rule.** Compare the current 25-move stall rule with a focus-based rule on the
same runs: moves spent after the goal stopped progressing. This is the measure that
decides whether the controller earns its place.

**Held-out games.** Same rule as Parts 1 and 2.

**Unit tests.** Each controller rule has a test with a focus record that fires it and one
that does not. Each log line names the rule that fired.

# Visual-Spatial Calculations Design (Part 4 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Visual-Spatial Calculations" section, pasted 2026-10-30. The source
names four tools and no requirements, so this part states what each tool would do in
our agent and what it would take to adopt it. Parts 1 to 3 define the stores, retrieval,
and metacognition that these calculations feed.

## 1. Requirements (from the source)

The source lists four tools:

- **Breadth-first search (BFS).**
- **Jump Point Search (JPS).**
- **Theta\*.**
- **Q-learning.**

It does not say which problem each tool solves for the agent. Section 3 maps each one to
a problem in the current agent. Section 5 records the calls I made.

## 2. What the current code does

The agent already runs three of the four ideas in some form, under other names. It has no
JPS, Theta*, or Q-learning.

| Tool | Where it exists | What it does | Status |
|---|---|---|---|
| BFS | `kinematics.py` `reachable` and `_walk_back`; `explore.py` `Graph.path_to_frontier`; `guided.py` path search | Shortest move count over a gait graph, or over the explorer's state graph. | Built in four places with the same loop. |
| Best-first search (A*-like) | `search.py` | Expands scenes by plan length plus weight times `Goal.distance`, using a heap. | Built. The heuristic is not checked for admissibility, so paths are not guaranteed shortest. |
| Optimal visiting order | `route.py` | Held-Karp for up to 6 targets, then nearest-neighbor with 2-opt. | Built. Not in the source list, but it is the spatial routing tool the agent uses. |
| JPS | none | | Missing. |
| Theta\* | none | | Missing. |
| Q-learning | none. I searched `arcagent` for reward, Q-table, TD, and epsilon and found nothing. | | Missing. |

Movement in the agent is not free-form. `kinematics.gaits` learns each action's effect:
a fixed step (`move`) or a slide until blocked (`slide`). Clicks are excluded from gaits.
A path is a sequence of learned actions, and only those are executable.

## 3. What each tool would do here

**BFS: keep and share.** BFS is exact for shortest move counts when every move costs one
action, which is the case here. The four copies (kinematics, explorer, guided, and the
walk back) differ only in their neighbor function. One shared function that takes a
neighbor function removes the duplication and gives one place to fix bugs.

**Best-first search: keep, and measure before changing.** `search.py` already does what
A* does, with `Goal.distance` as the heuristic. The gap is that the heuristic is not
guaranteed to be admissible, so the search can return a longer plan than the shortest one.
An admissible heuristic would fix that, but it may expand more nodes. This is a
trade-off to measure, not a bug to fix now.

**JPS: conditional, not built.** JPS speeds up uniform-cost grid search by skipping
symmetric expansions. Its pruning rules assume every move is a unit step in a fixed set of
directions. Our gaits break that assumption in two ways: a game's step size can be more
than one cell, and slides stop at obstacles. JPS applies only to a game whose learned
gaits are all unit steps. Whether any game is in that class, and whether the search time
justifies JPS, is unmeasured. Section 5 (D2) sets the gate.

**Theta\*: not adopted.** Theta* produces any-angle paths by drawing straight lines
between cells. The agent can only take the learned discrete actions, so an any-angle path
usually contains moves the game cannot make. It would fit a game with continuous movement.
I have not checked the 25 games for continuous movement. The survey from 2026-10-29
recorded action lists and colors, not movement types, so this is unverified.

**Q-learning: not in this build.** Q-learning learns the value of state-action pairs from
reward. In these games the reward is a level-up, which happens 6 to 10 times per game, and
a game over. A value table keyed on scene would be sparse. It would need the same canonical
features and store that Parts 1 and 2 define, and its cost would show up in the held-out
games. Section 5 (D4) sets the gate.

## 4. Behavior

Applies only to the BFS consolidation in this build. The other tools are gated.

- **Shared BFS.** One function takes a start, a neighbor function, a target test, and a
  visit limit, and returns the path and the depth. The limit is `KIN_LIMIT` for kinematics
  and the explorer's own bound for the state graph.
- **Equivalence.** For every caller, the shared BFS returns the same path and the same
  distances as the current copy it replaces, on the same inputs.
- **Bounds.** The shared BFS visits at most its limit of nodes and reports when it stops
  at the limit, so a caller can tell an empty result from a truncated one. Today
  `reachable` stops silently at `KIN_LIMIT` (4096 top-lefts); that silent stop is the
  behavior to change.

## 5. Decisions I made

These are my calls, changeable without changing section 1.

- **D1. BFS stays the default for distance.** Reason: exact for unit moves, and the
  simplest correct tool. Cost if wrong: none found; the gait model is already discrete.
- **D2. JPS gate.** JPS is built only if all three hold on the measured runs: (a) at
  least one game's learned gaits are all unit steps; (b) search and BFS time is a large
  share of move time in those games; (c) JPS returns the same plan length as BFS on those
  games. Reason: JPS adds code paths that only some games use. Cost if wrong: time spent
  on a tool that does not pay off.
- **D3. Theta* is out of scope.** Reason: the executable moves are discrete. Revisit only
  if a game with continuous movement is in the held-out set.
- **D4. Q-learning waits for the store.** It is built only after Part 1's store and Part
  2's retrieval exist, and only as a held-out experiment. Reason: a value table keyed on
  scene would overfit a single game, and its keys need the canonical features. Cost if
  wrong: an experiment with no result.
- **D5. Heuristic admissibility is measured, not assumed.** I will not change the
  heuristic in `search.py` until the plan-length gap is measured on real runs.

## 6. Test plan

**Shared BFS equivalence.** For each of the four current copies, a test feeds the same
inputs to the old and new function and asserts the same path and distances. Each caller
keeps its own test.

**Truncation.** A test with a limit below the reachable area checks that the result is
marked truncated and that the empty result (no path) is distinct from the truncated one.

**Search plan length.** On recorded runs, compare the plan length `search.py` returns
with the BFS shortest length over the same gait graph. The gap is the measure for D5.

**JPS gate.** Only if D2 is triggered: time BFS and JPS on the qualifying games, and check
plan lengths match.

**Profile.** Before any change, profile the move loop and report the share of time in
`kinematics`, `search`, `explore`, and `guided`. This decides whether D2 applies at all.

**Held-out games.** Same rule as Parts 1 to 3.

## 7. Open questions for Kameron

- **Q1.** Do you want an admissible heuristic in the best-first search (D5), even if it
  costs more expansions? Or is the current search, which is faster but not guaranteed
  shortest, the one to keep?
- **Q2.** Do any of the games you plan to test have continuous movement, such as a sprite
  that moves by pixels rather than cells? That decides whether Theta* stays out (D3).
- **Q3.** Is Q-learning meant as a learned policy that replaces the explorer, or as a
  value estimate that ranks frontier states? The second fits the store and retrieval
  design better, and is what D4 assumes.
- **Q4.** Should `route.py` (the visiting order over targets) be listed as a visual-spatial
  tool in the refactor? It is in the code but not in your list.

# Planning Design (Part 5 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Planning" section, pasted 2026-10-30. The source governs where it
differs from the current code. Parts 1 to 4 define the stores, retrieval, self and
metacognition, and spatial tools that a plan draws on. Part 4 (`2026-10-30-visual-spatial-design.md`)
covers the BFS and best-first search this part reuses.

## 1. Requirements (from the source)

- **P1. Decision science.** Planning is a way of deciding what to do in order to carry out
  tasks. Each move is a decision, and the decision rule should be stated, not implied.
- **P2. Decompose from known things.** Planning breaks a goal into tasks, using the
  attributes, events, rules, and experiences the agent already knows.
- **P3. Replan from the last fork.** When something unexpected happens mid-task, the agent
  replans from its last successful branch, not from its last step. Its example is a maze.
  If the newest fork is exhausted without success, the agent returns to the fork before
  it. This repeats until the level is complete.
- **P4. Simulate before moving.** Planning runs in simulation before any real move.
- **P5. Plan parts, not the whole.** A plan covers part of the end-to-end process, not all
  of it. The source says this gives the agent adaptability.

The source does not define a fork, what "exhausted" means, or the size of a plan part.
Section 5 proposes those and marks them as decisions.

## 2. What the current code does

The planner is `arcagent/mind/fluid.py` with the search in `search.py`. Its decision order
is written in the module docstring, steps 1 to 7 and the sub-steps under them.

| Requirement | Current code | Status | Gap |
|---|---|---|---|
| P1 decision rule | A fixed priority ladder in `fluid.py` `_decide`: game over, level change, forced move, bump, plan or follow, budget-tight step, indicator step, tester test, best partial plan, novelty. | Partial | The order is explicit and logged (each move records its branch and why), but no move is scored against the others. The ladder is not a utility or expected-value rule. |
| P2 decomposition | Goals come from heuristics in `GoalBook`, the executive turn, and the indicator. `search.py` composes steps toward a goal by predicting moves. | Partial | Goals are not split into subgoals. A goal is reached by one search, not by a tree of tasks built from rules. |
| P3 replan from fork | After a plan breaks (`plan_breaks`), `_plan` is cleared, and the next move runs a fresh search from the current scene. | Missing | No fork stack. The planner does not return to an earlier branch point after the newest one fails. The fresh search can rediscover the old branch, but nothing guarantees it. |
| P3 backtrack in a maze | `explore.py` `Graph.path_to_frontier` walks back to the nearest state with an untried action. That is backtracking, in the explorer. | Partial, explorer only | The fluid planner has no equivalent. The hybrid hands the level to the explorer after a stall, which is the only backtracking path in play. |
| P4 simulate first | `search` expands scenes with `predict` before any real move. `SEARCH_MAX_NODES = 3000` bounds the predictions. | Built | The simulation covers the goal search. The tester and novelty moves are not simulated. |
| P5 plan parts | `search` returns a full plan to a goal. When no full plan is found, the best partial plan's first step is taken and the rest is held as a plan toward its goal (`toward <goal id>`). | Partial | A plan is a path to the whole goal, not a bounded segment. Partial plans are held in full. |

**Stop rule.** A plan stops only on a miss that matters (`plan_breaks`, the rule in
`fluid.py` step 4). A miss about a mover or a goal sig stops it. Other misses are logged
and learned. After `STALL_AFTER = 2` failed attempts at one goal in one level, the goal is
set aside. This is the closest the code has to a replanning trigger, and it is
goal-level, not fork-level.

**Why the gap matters.** When a plan breaks in a maze, the planner searches again from
where it stands. If the first branch was the wrong one, the fresh search may choose it
again, because nothing records that it failed. Recording failed branches is what P3 asks
for.

## 3. Proposed structure

**Plan tree.** A plan is a tree of branch points, not a list. Each node records:

- `scene_key`: the scene the branch started from.
- `steps`: the moves tried from that node, in order.
- `status`: `open`, `exhausted`, or `succeeded`.
- `parent`: the node it branched from.

The tree is per level, reset on a level change. A game over keeps the tree and marks the
current branch failed, because the level restarts from the same frame.

**Replan rule.** When a plan breaks:

1. Mark the current branch `exhausted` if its goal did not hold.
2. Return to the newest ancestor branch with an untried step, and resume there.
3. If no ancestor has an untried step, search from the root.

This is the P3 maze rule, applied to the plan tree.

**Plan parts.** A plan is cut to a bounded segment of steps (the size is decision D3). The
segment ends at a checkpoint, a scene where a fact the segment depends on is first tested
or a goal sub-condition first holds. The next segment is planned from the checkpoint.

**Simulation.** Every segment is simulated with `predict` before any real move. The
simulation reuses `search`, with its node and time bounds.

## 4. Behavior

- **Branch record.** Each branch point is logged (`branch_open`) with its scene key and
  the moves it will try.
- **Backtrack.** A break logs `branch_exhausted` or `replan_from`, with the node resumed.
- **Termination.** Replanning stops at level completion or when the root has no untried
  step. The second case falls back to the explorer, as today.
- **Segment size.** A segment ends at its size bound or its checkpoint, whichever comes
  first. A segment that ends at the bound is logged as `segment_cut`.
- **Interaction with the stall rule.** `STALL_AFTER` counts failed segments at one goal,
  not failed plans. A segment that backtracks is not a failed attempt until its tree is
  exhausted.

## 5. Decisions I made

These are my calls, changeable without changing section 1.

- **D1. The decision ladder stays.** The fixed order from `_decide` is kept, with the
  logging it already has. Reason: it is explicit and tested, and changing it to an
  expected-value rule is a larger change than the requirements need. Cost if wrong: a
  decision rule that is wrong in an order we don't see. Q1 asks for a yes or no on
  expected value.
- **D2. Plan tree per level.** Branch points live in one tree per level, reset on a level
  change. Reason: P3 is about the same level, and a level change makes old branches
  invalid. Cost if wrong: failed branches in one level do not inform the next.
- **D3. Segment bound.** A segment is at most the depth of a goal search found in a
  typical run, which I have not measured. I'll set the bound from the recorded plan
  lengths before choosing a number. Reason: a bound that is too short makes the planner
  replan constantly, and one that is too long is the whole-process plan P5 rejects.
- **D4. Game over keeps the tree, marks the branch failed.** Reason: the level restarts
  from the same frame, so the failed branch is still the wrong one to try first.
- **D5. Simulation covers the goal search only.** The tester and novelty moves stay
  unsimulated. Reason: they exist to learn facts, and simulating them would use the facts
  they are meant to test.

## 6. Test plan

**Backtrack.** A maze fixture where the first branch dead-ends. The test asserts the
planner returns to the fork and tries the second branch before searching from the root.

**Exhaustion.** A fixture where every branch dead-ends. The test asserts the planner falls
back to the explorer after the root is exhausted, and logs each `branch_exhausted`.

**Segment bound.** A test that checks no segment exceeds the bound and that each cut is
logged. The bound itself is set in D3 from recorded data.

**Game over.** A test that checks the tree survives a game over, the current branch is
marked failed, and the next move resumes an older branch.

**Simulation.** A test that the goal search makes no real move before its plan is
complete, and that tester and novelty moves are not simulated.

**Measured effect.** On recorded runs, count moves spent on branches that had already
failed in the same level, before and after the tree. That is the measure of P3.

**Held-out games.** Same rule as Parts 1 to 4.

## 7. Open questions for Kameron

- **Q1.** Should the decision ladder (D1) be replaced by an expected-value rule, where
  each move is scored by the chance it advances a goal, or is the fixed order enough?
- **Q2.** Is a fork in your sense any point where the planner had more than one untried
  step, or only a point where the plan could go two different ways toward the same goal?
- **Q3.** When the planner returns to an older fork, should it keep the moves that worked
  on the way to the fork, or replay them from the start of the level?
- **Q4.** Should the explorer's backtracking (`path_to_frontier`) become the fluid
  planner's replan step, or should the two stay separate with the hybrid as the switch?

# Perform Design: Sequence List, Inhibition, Performance (Part 6 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Perform" section, pasted 2026-10-30. The source governs where it
differs from the current code. Parts 1 to 5 cover the stores, retrieval, metacognition,
spatial tools, and planning that this part uses.

## 1. Requirements (from the source)

The section has three parts.

**Sequence list**

- **Q1.** A list of sequential steps, in order, that completes a task.
- **Q2.** The list acts as the action list the agent uses.

**Inhibition**

- **I1.** A neural network runs alongside the rest of the system.
- **I2.** It connects objects to their adverse events, actions, and experiences that
  produce negative outcomes for the player.
- **I3.** It stops simulations and planning from taking an action that leads to an
  immediate, near-future negative outcome.

**Performance**

- **R1.** The agent writes code and performs actions to make progress in the level.
- **R2.** It uses the sequence list to write the code or to choose the actions.

The source names a neural network for inhibition and does not say how big it is, what it
is trained on, or whether it is learned online. Section 5 covers that.

## 2. What the current code does

**Sequence list.** The fluid planner keeps a plan as a list of steps (`_plan`, a list of
`PlanStep`). Each move pops the next step (`fluid.py`, step 4). The indicator adds a
sequence goal (`SEQ_SOURCE = "indicator"`), and its branches `sequence step` and
`sequence try` choose clicks in order (`fluid.py`, step 6). A level change clears the plan
(step 2). So the plan is the action list, but it lives for one level and is then dropped.
Nothing carries a successful sequence into a later level or game.

**Inhibition.** There are two implementations.

- **Program path.** `DisconfirmInhibition` (`modules/inhibition.py`) records each
  (frame, action) pair that went badly, for one of three reasons: `game_over`, `noop`, or
  `disconfirmed`. Veto sets are kept in working memory under a frame hash with a TTL. This
  is a lookup table, not a network.
- **Fluid path.** The fluid agent asks its inhibition module for vetoes on each option
  (`modules.inhibition.veto`, `fluid.py`). Plan steps honor four reasons: `game_over`,
  `no_effect`, `seen_no_effect`, and `undoes_progress` (`_PLAN_VETOES`). The search never
  expands a predicted game over (`search.py`, the first branch rule). The search also
  checks each predicted scene against the scenes already seen.

So inhibition runs in two places, search and the move loop. It is not a network. It tracks
four kinds of outcome, and the first three are the only ones learned from the game itself:
death, no change, and disconfirmed prediction. `undoes_progress` is the fourth.

**Performance.**

- **Scored path (hybrid).** The fluid agent picks each action and writes no code. The
  explorer picks actions from its graph. Nothing in the scored path writes code.
- **Code path (LLM).** The synthesizer (`synthesizer.py`), the program sandbox
  (`sandbox.py`, with allowlisted imports and a timeout), `toolbox.py`, and `tool_fix.py`
  let the LLM write programs and tools. `llm_drive.py` runs them. This path is separate
  from the hybrid.

Status: partial for Q1 and Q2 (a plan exists, but it doesn't persist). Partial for I2 and
I3 (rules, not a network, and only four outcome types). For R1 and R2, the scored path
does not write code. The code path does, but it is a separate mode.

## 3. Proposed structure

**Sequence record.** A sequence is an ordered list of steps that completed a goal, kept
with what it did.

- `id`: stable within the store.
- `goal`: the goal it completes, as a canonical goal record (Part 1, section 3).
- `steps`: the moves in order, each as an action key plus the features it was taken on.
- `runs`, `successes`: how often it has been tried and how often it completed the goal.
- `scope`: `level`, `game`, or `long`, as in Part 1.

A sequence is written when a plan completes its goal. It is read when the same goal comes
up again, and it is a candidate in the retrieval from Part 2.

**Inhibition store.** Inhibition becomes a set of adverse rules, kept in the Part 1 store
and retrieved through Part 2's index.

- `subject`: a thing kind (Part 1, D1), or `any`.
- `action`: an action key, or `any`.
- `event`: the adverse outcome: `death`, `harm`, `no_change`, `undoes_progress`, or
  `disconfirmed`.
- `evidence`: how often the rule's pattern led to the event.
- `status`: `candidate` or `validated`, as in Part 1.

A rule vetoes an action when its subject is present, its action matches, and its event is
expected within the search horizon. A veto is logged with the rule it came from.

**Network hook.** The inhibition store exposes one function: given a scene and an action,
return the predicted adverse events and the rules behind them. A network, if built later,
replaces the function and keeps the same return shape. This keeps the source's network
behind an interface we can test first.

**Performance.** The move loop writes a record of the step that produced each action:
which list (plan, sequence, explorer) and which step. Code written by the LLM path stays
in the sandbox and is logged the same way.

## 4. Behavior

- **Sequence write.** When a plan completes its goal, the sequence record is written with
  `runs` and `successes` set to 1. A level change does not clear it.
- **Sequence read.** When a goal is proposed and a sequence for it exists, the sequence is
  tried first, as a plan. A break ends it, and the failure is counted in `runs`.
- **Sequence validation.** A sequence that succeeds on three runs in a row is validated
  (D3).
- **Inhibition veto.** A vetoed action is skipped unless it is the only move left, in which
  case the forced branch takes it and logs `forced`. This is the same rule the fluid agent
  already follows.
- **Search.** Search prunes branches where an adverse rule fires with an event the horizon
  reaches. The predicted game over stays the first and hardest rule.
- **Log.** Each veto writes its rule id and event. Each sequence step writes its sequence
  id.

## 5. Decisions I made

These are my calls, changeable without changing section 1.

- **D1. Sequences persist beyond one level.** A sequence is written on success and kept
  in the store. Reason: Q1 says the list completes a task, and a task can recur at a later
  level or game. Cost if wrong: stale sequences that the validation step must retire.
- **D2. Inhibition is rules first, network later.** The source names a network. This build
  stores adverse rules behind the interface in section 3. Reason: we have no training set
  of adverse events for any game, and a rule can be checked in a run log. Cost if wrong:
  a network that would have generalized better is delayed. Q2 asks whether to build it
  now.
- **D3. A sequence is validated after three successes in a row.** The source gives no
  number. Three matches the solid threshold used elsewhere, scaled down for sequences,
  which are checked against a whole goal rather than one fact.
- **D4. Harm is an adverse event only when a counter or bar falls.** This needs a
  definition of a counter. The fluid path already masks move counters as noise
  (`noise.py`), so their cells are known. Reason: it is the only harm signal the games show that is not death.
  Cost if wrong: harm events that are missed or invented. Q3 asks for a definition.
- **D5. The scored path stays action-only in this build.** The code path stays a separate

# Grit and Perseverance Design (Part 7 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Grit" and "Perseverance" sections, pasted 2026-10-30. The source
governs where it differs from the current code. Part 6 (`2026-10-30-perform-design.md`)
defines the adverse rules that perseverance reads, and Part 5 (`2026-10-30-planning-design.md`)
defines the plan tree that a gate would stop.

## 1. Requirements (from the source)

**Grit: gates**

- **G1.** Stop the agent from spending all its time on one action or task.
- **G2.** Stop the agent from spending an excessive number of tokens on one action or
  task. The source calls this a sign of over-engineering.

**Perseverance**

- **P1.** An adverse outcome can be predicted with some probability. Perseverance can
  override a medium probability and let the agent try the action anyway, because the
  good outcome (the example is a critical hit) also has a probability and may happen.
- **P2.** Perseverance needs a reason. The source gives two: there is no other way around
  (the example is an enemy blocking the path), or going through the adverse outcome gives a
  higher score.
- **P3.** The example: a sword fight where losing is certain unless the player lands a
  critical hit. Perseverance overrides inhibition and attacks anyway, even though the
  player may die.

The source gives no numbers for either the gates or the probability bands. Section 5
states the values I used, and each one is marked as a placeholder until measured.

## 2. What the current code does

**Time gates.** Each gate is per move or per turn, not per task.

- `search.py`: `SEARCH_TIME_S = 1.0` wall-clock cap per search, and `SEARCH_MAX_NODES =
  3000` predictions.
- `fluid.py`: `TURN_DEADLINE_S = 30.0` (the longest a move waits for its turn), and
  `MAX_TESTS_PER_ATTEMPT = 200` test moves per level attempt before the tester is skipped.
- `llm_drive.py`: `DRIVE_TURN_S = 90.0` per drive or fix turn.
- `budget.py`: the move budget is read from the game's own counter bar. It is the game's
  limit, not ours.
- `fluid.py` `STALL_AFTER = 2`: after two failed attempts at one goal in one level, the
  goal is set aside. This is a per-task gate, and it counts attempts, not time.
- `hybrid.py` `STALL_MOVES = 25`: after 25 fallback moves in a row, the explorer takes the
  level. This is a per-task gate on moves.

**Token gates.** `TURN_MAX_TOKENS = 1536` (fluid turn) and `DRIVE_MAX_TOKENS = 4096`
(drive turn) cap each reply. `llm_drive.py` `DRIVE_CUTOFF = 0.1` stops a turn from starting
when less than a tenth of the game's budget is left. I searched `fluid.py`,
`llm_drive.py`, and `budget.py` for a cumulative token count per task and found none. The
caps are per reply, and nothing counts tokens across a task.

**Perseverance.** The closest mechanisms are these.

- **Forced move.** `fluid.py` `_forced` takes the one action left after plan vetoes. It
  never takes an action whose veto reason is in `_PLAN_VETOES`, and that set includes
  `game_over`. So a predicted death is never forced, even if it is the only move.
- **Commit probes.** `fluid.py` step 3 skips the `seen no effect` veto when a goal is
  reached but not yet confirmed. It still honors a predicted game over.
- **Stall handover.** The explorer takes over after a stall. This is a change of method,
  not a override of an adverse prediction.

Vetoes are binary. A rule vetoes or it doesn't. Nothing records a probability for the
adverse outcome, and nothing records a reason for overriding one. The forced move and the
commit probe are the only overrides, and neither logs a probability.

Status: gates are partial (time and attempt gates exist, token gates are per reply only).
Perseverance is missing as a concept. The code has two narrow overrides with no reason
record.

## 3. Proposed structure

**Task record.** Every goal attempt and every level attempt has a record.

- `wall_s`: wall-clock time spent.
- `tokens`: tokens spent on LLM turns for the task (zero on the scored path).
- `moves`: moves spent.
- `progress`: whether a goal distance fell (from the progress monitor, Part 3).

**Gates.** The task record is checked after each move. A gate that trips ends the task
and hands it to the next method (the explorer, or the next goal in the ranked list). Each
trip is logged with the gate's name and the record's values.

**Over-engineering signal.** A task whose `tokens` exceed the expected value for its
goal kind, with no `progress`, is flagged in the log. The flag does not stop the task. It
is an input to the controller in Part 3.

**Adverse estimate.** For each adverse rule (Part 6), the estimate is a Beta posterior on
the probability of the adverse event, given the trials in which the rule's pattern
occurred.

- `hits`: trials where the event happened.
- `trials`: trials where the pattern occurred.
- `p`: the posterior mean under a Beta(1, 1) prior.

**Override.** Perseverance is a rule that returns an override decision. It needs both:

1. A probability band for the adverse event: medium (see D2).
2. A reason, one of:
   - **No other way.** The search with the vetoed move removed returns no plan to the goal.
   - **Score.** The goal's score gain (Section 5, D3) exceeds the expected cost of the
     adverse event.

**Override trials.** A permitted override is a trial. Its result updates the adverse
estimate. The override is allowed again only while the estimate stays in the medium band,
and at most `PERSIST_TRIALS` times per rule per level (a placeholder value, D4).

## 4. Behavior

- **Gate trip.** A gate that trips logs `gate_trip` with its name, the task record, and
  the next method. Nothing is silently skipped.
- **Override.** An override logs `perseverance` with the probability, the reason, and the
  rule id. The move is taken as a normal move.
- **Certain adverse event.** A predicted event at or above the certain band is never
  overridden, and a predicted game over stays in `_PLAN_VETOES`. This keeps the current
  rule that death is never forced, even when it is the only move.
- **Low adverse event.** A rule below the medium band is never overridden. The veto
  holds as it does now.
- **Repeated failure.** When an override ends in the adverse event, the estimate rises. If
  it crosses into the certain band, further overrides stop.

## 5. Decisions I made

These are my calls. The values marked as placeholders have not been measured.

- **D1. Gates are per task, checked per move.** Reason: the source names time and tokens
  per action or task, and the current gates are per move or per reply. Cost if wrong: the
  check runs on every move even when no task is near its limit.
- **D2. Probability bands (placeholder).** Certain: p at or above 0.9. Medium: p from 0.2
  to 0.9. Low: p below 0.2. Reason: the source says "some probability" and "medium level,"
  so the bands need edges, and these are a first guess. Cost if wrong: overrides at the
  wrong probabilities, which the estimate and the trial cap are meant to catch.
- **D3. Score as the reason.** The score for a level is `min(115, (human / agent)^2 * 100)`,
  weighted by level depth, as in the competition scoring. An override on score is allowed
  when the gain in that score from the goal exceeds the adverse cost. The adverse cost is
  the moves lost to a restart, which feeds the same formula. Reason: P2 names score as a
  reason, and this is the score. Cost if wrong: the estimate of moves lost is rough.
- **D4. Trial cap (placeholder).** `PERSIST_TRIALS = 3` override trials per rule per
  level. Reason: enough to see a probability event happen (the critical hit) without
  letting a bad estimate repeat unbounded. Cost if wrong: a real critical hit could need
  more trials.
- **D5. Tokens are logged per task, not gated, until measured.** The token gate is the
  over-engineering flag only. Reason: nothing in the runs tells us the expected token count
  per goal kind, so a gate would use a guessed number. Cost if wrong: a task that
  over-engineers is flagged but not stopped.

## 6. Test plan

**Gate trips.** Fixtures where a task passes its time limit, its move limit, and its
token limit. Each trips its gate, logs it, and hands off to the next method.

**Probability estimate.** A test that the Beta posterior moves toward the observed rate,
and that a rule with no trials stays at the prior.

**Override bands.** A test that a certain event is not overridden, a low event is not
overridden, and a medium event with a reason is overridden and logged.

**Reason.** A test where no plan exists without the vetoed move (the "no other way" reason)
and the override is allowed. A test where a plan exists and the score gain is below the
cost, and the override is refused.

**Repeated failure.** A test that the estimate rises after each failure and that overrides
stop once it crosses into the certain band.

**Sword fixture.** The source's example: a fixture with a critical-hit probability of
about 0.3 and a certain death without it. The override is allowed for up to
`PERSIST_TRIALS`, and it stops after the estimate crosses into the certain band.

**Measured effect.** On recorded runs, count gate trips per task, and count overrides and
how many of them ended the level. The second number is the measure of P3.

**Held-out games.** Same rule as Parts 1 to 6.

## 7. Open questions for Kameron

- **Q1.** Is the time gate per move, per level attempt, or per whole game? The competition
  rules set a runtime limit that I haven't checked for this spec.
- **Q2.** Should the token gate count LLM tokens only, or every model call in the run,
  including any model we ship?
- **Q3.** Are the probability bands (D2) right? I used 0.2 and 0.9 as edges. Give numbers
  or a rule and I'll replace them.
- **Q4.** Is "no other way around" enough as a reason, or should it also need the score
  check in D3?
- **Q5.** Should an override trial count against the game's move budget from `budget.py`?
  A trial that dies costs a life, and a life is a budget unit in some games.

# Prediction, Level Modeling, and Simulation Design (Part 8 of the refactor spec)

spatial tools, planning, perform, and grit that this part draws on. Part 6 defines the
sequence record, and Part 7 defines the adverse-event probabilities this part reuses.

## 1. Requirements (from the source)

**Prediction**

- **R1.** Prediction writes to nothing except two lists: the sequence list and the
  hypothesis list. It only reads everything else.

**Level modeling**

- **L1.** Hypothesis list: a guess list of ways to complete the level, ranked by the
  highest probability of completing the level task.

**Simulation**

- **S1.** A copy of the level is rebuilt as the current state.
- **S2.** The player plays the level in simulation, pulling from memory to test hypotheses.
- **S3.** The agent predicts only a few moves at a time, each with a probability estimate.
- **S4.** The simulation also predicts enemy movement and adverse events and experiences.
- **S5.** The simulation uses the visual-spatial tools (Part 4) to aid its predictions.

**Sequence list (second definition)**

- **Q1.** The sequence list holds the highest probable next move or moves that let the
  player reach the next task.

The source puts a probability on the hypothesis list and on each predicted move. It does
not say how those probabilities are computed. Section 5 proposes a way and marks it as a
decision.

## 2. What the current code does

**Where the probability is missing.** Facts already record evidence (`hits`, `misses`), and
the fact status (`candidate`, `solid`, `thin`, `broken`) is a threshold on that evidence.
Nothing turns the evidence into a probability, and nothing multiplies probabilities along a
path. Without that, the source's ranking by probability cannot be computed.

## 3. Proposed structure

**Fact probability.** Every fact has a probability of being right, from its evidence.

- `p_fact = (hits + a) / (hits + misses + a + b)`, a Beta posterior mean with prior
  `a, b` (D2).
- The same form is used for adverse rules (Part 7) and for sequence success (Part 6).

**Move probability.** A predicted move has the probability of the fact that produced it.
A move predicted from a sibling fact (`lent`) uses the sibling's probability (`lent` is
already recorded in `Prediction`).

**Path probability.** A hypothesis (a path to a goal) has the product of its move
probabilities (D3).

**Hypothesis list.** The hypothesis list is built as follows.

1. Run the search over the goal guesses, as now.
2. For each goal the search reaches, compute the path probability of its plan.
3. Rank the goals by path probability, ties by the current score.
4. Keep the top `k` (D5).

The list is written after each search and read by the planner (Part 5). It is the
hypothesis list the source asks for.

**Sequence list (live).** The sequence list is the first `h` moves of the top hypothesis,
with each move's probability. It is written with the hypothesis list. Part 6's sequence
record is the completed version: a sequence list that reached its task is saved.

**Enemy motion.** An uncontrolled mover with no usable fact is predicted still, as now, but
its prediction is marked `assumed`. When the observed frame shows it moved, the miss is
logged against the assumption. Enough of those, and the mover gets a fact by observation.

## 4. Behavior

- **Prediction.** `predict` stays read-only. The hypothesis and sequence lists are written
  by a separate step after the search.
- **Probability bounds.** A path whose probability falls below `P_MIN` is not expanded
  further (D3). The search logs the bound it hit.
- **Horizon.** The sequence list holds at most `H` moves (D4). The planner (Part 5) cuts
  its segments at the same `H`.
- **Adverse events.** A predicted adverse event with probability from Part 7 is attached to
  its move. A move whose adverse probability is in the certain band is never followed
  (Part 7).
- **Assumed still.** Every assumed-still prediction is counted. A miss on an assumed-still
  mover is logged as `assumption_missed`.

## 5. Decisions I made

These are my calls. The values marked as placeholders have not been measured.

- **D1. Learning writes facts, not prediction.** The source says prediction writes only the
  two lists. This build keeps `predict` read-only and has the learning step write the facts,
  because learning needs the observed frame and prediction does not have it. Cost if wrong:
  the source's rule is broken on a technicality. Q1 asks whether the rule is strict.
- **D2. Beta prior of 1 and 1.** A new fact starts at 0.5, the same uninformative prior as
  Part 7. Reason: one set of numbers for every probability in the store.
- **D3. Independence and the bound.** Path probability is the product of move
  probabilities, which assumes the moves are independent. They are not, but the product is
  a stated, testable approximation. `P_MIN = 0.05` (placeholder). Cost if wrong: paths with
  correlated risk are over- or under-counted, which the calibration test in section 6 will
  show.
- **D4. Horizon `H = 5` (placeholder).** Reason: it matches the segment bound I'd set in
  Part 5 (D3), and five moves is short enough to check against the observed frame.
- **D5. Hypothesis list `k = 5` (placeholder).** Reason: the planner reads the top few, not
  the full list. Same reasoning as Part 2's D3.
- **D6. Enemy motion is assumed still until observed.** Reason: no fact means no evidence,
  and the current code already does this. The change is that the assumption is logged.

## 6. Test plan

**Read-only prediction.** A test that `predict` changes no field of `FactMemory`, the goal
book, or the plan, on a set of random scenes and actions.

**Probability.** A test that `p_fact` moves toward the observed rate, and that a fact with
no evidence stays at 0.5.

**Calibration.** On recorded runs, compare predicted move probabilities with the observed
rate, in bins. A well-calibrated store has the observed rate near the predicted one in each
bin. This is the test of D3's independence approximation.

**Hypothesis ranking.** A fixture with two goals where the cheaper one has the lower path
probability. The ranking must put the higher path probability first.

**Sequence list.** A test that the sequence list has at most `H` moves and that each move's
probability is the product of its facts'.

**Enemy assumption.** A fixture where an uncontrolled mover moves with no fact. The test
asserts the prediction is marked `assumed` and the miss is logged.

**Held-out games.** Same rule as Parts 1 to 7.

- **Q2.** Is the independence approximation (D3) acceptable for the first build, with the

# Curiosity Design (Part 9 of the refactor spec)

Status: draft for review, 2026-10-30. Nothing is built from this document yet.
Source: Kameron's "Curiosity Questions" section and the "Planning Process" loop, pasted
2026-10-30. The source governs where it differs from the current code. Parts 1 to 8
cover the stores, retrieval, metacognition, spatial tools, planning, perform, grit, and
prediction that curiosity draws on.

## 1. Requirements (from the source)

**Curiosity flags**

- **C1.** Each item on the map carries flags.
- **C2.** A flag can be labeled `check`. A mouse click or the character touching a
  `check` flag identifies the outcome.

**Four stages of curiosity**

- **H. Hook (attention and recognition).** The agent detects something novel or out of
  place, then checks memory to see whether the item matches a known category.
- **I. Investigation (decoding).** The agent works out what the item does, how it works
  (buttons, textures, moving parts), and why it is there (context, design, material).
- **A. Personal assessment (value).** The agent weighs the item's value against its cost.
  The source adds a social check: what others think of the item.
- **M. Mental simulation (projection).** The agent places the item in its routine and asks
  what problem it solves.

**Planning process loop (given with this section)**

Framing, then objectives and rules, then alternative generation, then modeling and
trade-offs, then execution, then evaluation and learning, then back to framing.

Two of the source's ideas do not fit a single-player game agent, and section 5 says so.
The social check (what others think) has no counterpart here, because the agent plays
alone. The source also leaves open where the planning loop runs. This draft treats it as
the loop that the agent's own planning follows, and Q4 asks you to confirm that reading.

## 2. What the current code does

**Flags.** Nothing on a map item is labeled `check`. The closest thing is the search's
frontier: `SearchResult.frontier` holds the unknown `(label, subject)` pairs the search met,
in first-met order (`search.py`). A frontier pair is an unchecked outcome, which is what a
`check` flag would be. The frontier is not stored on the item, and it is cleared on a level
change (`fluid.py` step 2).

**Hook.** Novelty is detected in three places.

- `kinds.KindBook` gives each thing an identity class across looks, so a changed look is
  matched to a known kind. This is "have I seen this before" for appearance.
- A pair with no fact is an unknown, so a new sig is novel by default.
- The novelty fallback (`fluid.py` step 7, `explore novel`) searches for states the agent
  has not seen on this level.

**Investigation.** Touch and near contexts are learned (`facts.touch_contexts`,
`facts._learn_touch`). A touch that changes something is recorded as a fact keyed by the
action, the subject, and the context. Modes (`modes.py`) learn what a click on a thing
does to its selection marks. Blockers and walkable colors are learned per sig. The
investigation is done by moves that touch things, which is what the source describes.

**Assessment.** `GoalBook.ranked` weighs a goal by its prior, its salience, and its
distance (`prior * salience / (1 + cost)`). That is a value and a cost, computed for goals
rather than for items. Nothing scores an item by its own value.

**Simulation.** `search` predicts a child scene for each action (`predict`), and the goal
distance decides which scenes it expands. A goal whose plan reaches the item is the
closest thing to "how would I use this." The search does not ask what problem the item
solves for the agent; it asks whether a goal holds.

**The planning loop.** The fluid agent runs the same sequence on each move, in its
decision ladder (`fluid.py`, steps 1 to 7). Framing is the level model
(`FactMemory.new_level`, the goal book). Objectives and rules are the goals and the facts.
Alternatives are the goal guesses and the frontier. Modeling and trade-offs are `predict`
and `search`. Execution is the move. Evaluation and learning are `learn`, `check`,
`fluid_sleep`, and `learn_win`. A level change starts framing again. The loop exists; it
is implicit in the code rather than named.

**Test choice.** The fallback test (`tester.choose_test`, `fluid.py` step 6) picks an
unknown pair from the frontier to test, using the Voi module's disagreement measure
(`modules/voi.py`). It runs only after the plan, the sequence steps, and the partial plan
have had a chance. A `check` moves through this same path.

Status: partial. The stages are present in the code as separate mechanisms. There is no
item-level record that ties them together, and no flag state.

## 3. Proposed structure

**Flag record.** Each thing on screen has a flag record, kept in the level model.

- `thing`: the thing's id (tracker id) and its kind (Part 1).
- `state`: `new`, `check`, `checked`, or `ignored`.
- `source`: `novel_look`, `unknown_pair`, or `changed`.
- `outcome`: the fact keys learned from the check, once there are any.

A flag is set to `check` when the thing's look is new (`novel_look`), or when a frontier
pair names it (`unknown_pair`). A flag is set to `checked` when a touch or click on the
thing has written a fact, and the outcome is the fact keys.

**Assessment.** A `check` flag gets two numbers: a value and a cost.

- `value`: the expected information from the check, from the Voi measure. Where the flag's
  thing is a goal sig, the goal's prior adds to it (the source's "do I need this").
- `cost`: the moves to reach the thing (kinematics distance), and one move for the check
  itself.

**Projection.** Before a check is taken, the search runs once with the thing's assumed
outcome, to see whether the outcome reaches a goal in a few moves. A check whose projected
outcome reaches a goal is ranked above one that does not. This is the source's mental
simulation (M), carried out by the search the planner already has.

**Planning loop.** The loop is written as the stage names of `fluid.py` with each stage's
owner, so a run log shows which stage made each move. No new logic is needed for the loop
itself. Section 4 gives the log events.

## 4. Behavior

- **Set.** A new look or a frontier pair sets a flag to `check` and logs `flag_set` with
  its source.
- **Check.** A move that touches or clicks a `check` thing logs `check` with the thing, the
  action, and the outcome facts. The flag becomes `checked`.
- **Ranking.** Among `check` flags, the one with the highest value per cost is taken first,
  but only after the plan and sequence steps (`fluid.py` steps 4 and 5) have had their
  turn, as today (D3).
- **Stage in the log.** Each move's log entry names its loop stage: framing, objectives,
  alternatives, modeling, execution, or evaluation.
- **Level change.** Flags reset with the level model. Facts from checks stay (Part 1).

## 5. Decisions I made

These are my calls, changeable without changing section 1.

- **D1. Flags are derived, not designer-set.** The source has a designer label the flag
  `check`. The agent can't see a designer, so the flag is set from what the agent does not
  know yet: a new look or an unknown pair. Reason: this is the only way to set flags
  without a human in the loop. Cost if wrong: flags for things that don't matter.
- **D2. The social check is not built.** Reason: the agent plays alone and has no other
  players' opinions. The closest analogue is a cross-game store (Part 1), and that is a
  store of the agent's own experience, not social validation. Cost if wrong: none for the
  agent; the source's stage is simply absent.
- **D3. Checks wait behind the plan.** A `check` is taken only after the plan and sequence
  steps. Reason: the current ladder already puts exploration after exploitation, and
  changing that order is a larger change than the requirements need. Cost if wrong: an
  item that would have changed the plan is checked late.
- **D4. Value is the Voi measure, plus the goal prior when the item is a goal sig.** Reason:
  Voi is already computed for the fallback test, and the goal prior is already computed for
  goals. Cost if wrong: value is a rough sum of two measures on different scales. The
  calibration test (section 6) checks the sum.
- **D5. The loop is named in the logs, not rebuilt.** Reason: the stages exist. Rebuilding
  them would break the tests that already cover them. Cost if wrong: a loop that is named
  but not enforced.

## 6. Test plan

**Flag set.** A fixture with a new look and a frontier pair. The test asserts each sets a
`check` flag with the right source.

**Check outcome.** A fixture where a click on a `check` thing changes a sprite. The test
asserts the flag becomes `checked` and the outcome fact exists.

**Ranking.** Two `check` flags, one with higher value per cost. The higher one is taken
first, after a plan step is available.

**Projection.** A fixture where a check's assumed outcome reaches a goal in two moves, and
a second check whose outcome reaches nothing. The first is ranked above the second.

**Calibration.** On recorded runs, compare the value of each check with the information the
check gave (the number of facts it wrote). A value that rises with the facts written is a
sign the Voi-plus-prior sum is ranking usefully (D4).

**Loop log.** A test that each move's log entry names exactly one loop stage.

**Held-out games.** Same rule as Parts 1 to 8.
